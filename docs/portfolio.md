# Portfolio Goals

[English](portfolio.md) | [한국어](portfolio.ko.md)

The repository itself is the portfolio. Keep the plan, progress, code, examples, architecture decisions, and measured results together. Add an item only when there is real evidence.

## Target artifacts

- [ ] A README with the problem, input/output example, and reproducible quick start
- [ ] A working CLI release that runs a complete change-to-report cycle
- [ ] Synthetic normal-change and seeded-defect fixtures with fixed Git refs
- [ ] Example QA reports with test selection reasons, logs, candidate-test results, and residual risk
- [ ] Architecture decisions explaining when LangChain, RAG, LangGraph, MCP, or an API were added
- [ ] Evaluation results: detected/missed defects, test quality, run time, model cost, review effort
- [ ] Failure cases and honest limits
- [ ] English main documents with linked Korean translations
- [ ] A demo another developer can reproduce using public materials

## What the finished portfolio should answer

1. Which judgment was hard to automate with rules alone?
2. How are model errors detected or contained?
3. What defects were found or missed, and under what conditions?
4. Which architecture choices improved the system, and what did they cost?

Do not turn an unmeasured target into a claimed result. Keep all examples in the public toy project or synthetic fixtures.
